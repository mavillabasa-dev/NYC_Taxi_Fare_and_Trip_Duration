03

Four pieces, one system

Presenter: Keyneth Lara1:30

English Script

So this is what we actually built — four pieces that fit together.

First, an offline pipeline. One command takes the raw trip file from the city — three and a half million rides in May of 2022 — cleans it, engineers the features, trains the models and writes a single artifact. End to end, it runs in about seventy-five seconds.

Second, the model itself. Two tuned LightGBM regressors: one for fare, one for duration. They travel inside one file, together with the code that transforms the input, so the serving side never needs to know how they were trained.

Third, the API. FastAPI, two endpoints. Predict takes a trip and returns both numbers. Health tells you whether the model is loaded and which version.

And fourth, the dashboard — a Streamlit app where you pick two zones on a map and get the prediction, without touching JSON.

Around all of that: Docker Compose for both services, seventy-one tests, and continuous integration that rebuilds the container and checks the model really loads on every single push. William will take you through how these fit together.

Spanish Script

Esto es lo que construimos: cuatro piezas que encajan entre sí.

Primero, un pipeline offline. Un solo comando toma el archivo de viajes de la ciudad —tres millones y medio de viajes de mayo de 2022—, lo limpia, genera las variables, entrena los modelos y escribe un único artefacto. De punta a punta corre en unos setenta y cinco segundos.

04

One file crosses the line

Presenter: William Vera1:30

English Script

Thanks, Keyneth. This is the whole system on one slide, and the important part is the dashed line down the middle.

On the left, everything runs on our machines. We download the trip data, the zone lookup table and the taxi zone shapefile; we clean the data, we split it by time, we fit the feature pipeline, we train.

On the right, everything runs inside a container. FastAPI loads a model and answers requests, and the dashboard talks to that API over HTTP — it never loads a model itself.

And between them, one file. Model dot pickle. That is the only thing that crosses.

We enforced that on purpose. The Docker build context is the API folder, so our training code is physically not in the image. If the artifact needed to import anything from it, the container would fail to start — and we would know immediately, because continuous integration checks exactly that on every push.

This is what makes the demo you are about to see honest. The API is not reaching back into a notebook. It only has the file.

05

Only what is known at pickup

Presenter: William Vera1:10

English Script

The second decision that shaped everything was what the model is allowed to know.

The raw data has nineteen columns, and most of them only exist after the ride is over: the drop-off time, the total amount, the tip, the tolls, the payment type. All of those correlate beautifully with the answer — and all of them would have been cheating. We drop them in one explicit step, and there is a test that fails if any of them ever reaches the model.

What is left is six inputs: the two zones, the pickup time, the passenger count, the rate code, and the trip distance. From those six we derive twenty-nine features — the hour encoded as a cycle, weekend and rush-hour flags, zone centroids from the shapefile, straight-line and Manhattan distances, and an encoding per zone.

One honest caveat. Trip distance is the metered distance of the completed trip. In production you would use a routing estimate instead. We wrote that assumption down rather than hiding it.

Spanish Script

La segunda decisión que marcó todo fue qué tiene permitido saber el modelo.

Los datos crudos tienen diecinueve columnas, y la mayoría solo existe después de que el viaje terminó: la hora de bajada, el monto total, la propina, los peajes, el tipo de pago. Todas correlacionan muy bien con la respuesta, y todas habrían sido trampa. Las eliminamos en un paso explícito, y hay un test que falla si alguna llega al modelo.

Lo que queda son seis entradas: las dos zonas, la hora de subida, la cantidad de pasajeros, el código de tarifa y la distancia del viaje. A partir de esas seis derivamos veintinueve variables: la hora codificada como ciclo, banderas de fin de semana y hora pico, centroides de zona sacados del shapefile, distancias en línea recta y tipo Manhattan, y una codificación por zona.

Una advertencia honesta: la distancia es la que marcó el taxímetro al terminar el viaje. En producción se usaría una estimación de ruta. Dejamos ese supuesto documentado en lugar de esconderlo.
