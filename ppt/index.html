The dataset · trap 01

There are no coordinates

The TLC removed latitude and longitude in 2016. Any brief that says “pickup and dropoff coordinates” is describing a dataset that no longer exists.

The dataset · trap 02

Half the columns are cheating

Allowed — known at pickup
tpep_pickup_datetime PULocationID DOLocationID passenger_count RatecodeID VendorID trip_distance *
Banned — only exists after the ride
tpep_dropoff_datetime fare_amount total_amount tip_amount tolls_amount extra mta_tax improvement_surcharge congestion_surcharge airport_fee payment_type store_and_fwd_flag

* One honest asterisk. trip_distance is the metered distance of a finished trip. We use it, and we write the assumption down — in production it would be a routing estimate, not a fact.

7 allowed 12 banned · a test asserts none of them reach the model

What 3.6 million rides told us

Cleaning is the model

Distance against fare correlates 0.01 on the raw file. Drop the impossible rows and the same pair correlates 0.95.

Speed is the real filter

The worst record implies 7,267,627 mph. Distance and duration each look fine alone — only together do they betray it.

Rate codes are separate worlds

Standard $12.53 / 16 min · JFK $50.83 / 52 min · Newark $65.00 / 44 min.

Phase 03 · Modelling — T-109

Accuracy is only half the score

How we choose

A stated trade-off, not a leaderboard

The winner is picked on accuracy and inference latency together. A model that is slightly better and far slower does not win — it has to answer a live request.

MAERMSEMAPE R²train timeinference time

Then error analysis on the winner: residuals by hour, by borough, by trip length, and on the airport rate codes.

The artifact the acceptance test

It has to survive on its own

models/model.pkl carries the fitted preprocessing pipeline, the model, the exact feature order, and a version string.

The test
It loads and predicts in a fresh interpreter with src/ absent from the path.
Because inside the container, src/ does not exist.

Whichever library wins also becomes a pinned line in api/requirements.txt.

Metrics in dollars and minutes never in log units

Make it real, then make it hold

T-111 frontend

The demo people actually see

Pick a pickup zone, a dropoff zone and a time. Get both numbers, drawn on an NYC choropleth. If the API is down, it says so — it does not show a stack trace.

T-112 tests

Proof, not confidence

Unit tests on every cleaning rule, a leakage test that fails if a banned column reaches the model, and integration tests hitting /predict and /health.

T-113 latency

A budget, and a measurement

Load test reporting p50, p95 and p99. We state the budget first, then measure whether we meet it — and optimise once, with numbers before and after.

T-114 devops

One command, any machine

Pinned requirements including the winning model’s library, a healthcheck wired to /health, the dashboard as its own service, and make run.

Retrain on the host restart the container — no rebuild

Does rain change the ride?

Historical hourly NYC weather, cached locally and joined on the pickup hour. Then retrain, and report the difference against our chosen model.

The condition
Adopted only if the gain is worth a live weather call sitting inside every request.
T-118 demand

Where will the next ride be?

Pickups counted per zone per time bucket, then a time-series model that predicts demand by region — shown on the same NYC map.

The condition
A separate module and notebook. It must not touch the fare and duration pipeline.

Both are off the critical path. Neither one is allowed to put the main deliverable at risk.
